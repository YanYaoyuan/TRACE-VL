## StreamingBench 压缩包库存修复

A100 在训练前报“6 annotations, 0 IDs”。本地读取官方六个 CSV 重现：这些文件确实没有视频 ID/路径列；Proactive_Output_50 的题号也不是视频号。现在直接从用户已有 ZIP 中读取媒体文件名，只读中央目录，不解压 benchmark，不修改分组/损失或关闭排重。CSV 支持 UTF-8 BOM。损坏 ZIP、只有题号且没有媒体的目录仍拒绝训练。

新增三个回归：无视频列的 CSV + 嵌套 ZIP 正常识别且禁止读取视频正文；损坏 ZIP 即使已有部分 ID 仍阻断；空 ZIP + 题号不算排重完整。新模块 29 项测试通过，与 OVO 转换/归档测试合计 44 项全部通过。官方六个 CSV 加人工 ZIP 布局的复现检查通过；未访问 A100 原始压缩包，故不宣称已验证其完整性。

格式来源：[官方六个 CSV](https://huggingface.co/datasets/mjuicem/StreamingBench/tree/main/StreamingBench)，[官方媒体整理脚本](https://github.com/THUNLP-MT/StreamingBench/blob/main/src/data/move_video.py)。本次排重仍限于标注/媒体文件名，不代表跨名称或重新编码视频的感知去重。

## CPU 数据准备性能修复

新增有上限的 spawn 进程池，逐视频保存核验记录；单解码器单线程。串行/双进程对相同真实测试视频产生完全一致的帧数、时间和 SHA256，损坏视频分别记录，重跑复用成功视频记录。归档测试含 100 个无关成员和两个目标，完整路径匹配仅调用两次；原有歧义和分卷测试保留。目录扫描减少无关文件的 stat/resolve 调用，阶段进度每 10 秒输出。

本机 16 个真实视频、7,326 帧的小规模核验测量：单进程 9.325 秒，4 进程 3.829 秒，核验结果一致。测量顺序为先串行后并行，未清除操作系统文件缓存，因此不能把该比值解释为严格冷缓存加速比，更不是 A100/NAS 吞吐承诺。未改动样本选择、划分、特征或训练设置。

本次最终整套回归：266 passed、1 skipped，38.84 秒；保留一条旧 v3 tensor-to-scalar warning。Ruff 和启动器 `bash -n` 通过。

## 独立归档并行读取（同日后续修复）

操作者的 A100 日志显示：主要耗时在 `media-probe-and-extraction`，约 26 分钟扫描到 250 个归档中的第 50 个，尚未进入多进程解码。此前的 32 worker 配置仅作用于解码，不能加速这一段。该数字不是完整运行耗时估计。

新增有上限的独立归档读取队列，event-state 默认 8 路；每个 gzip/tar/分卷仍按自身顺序读，完成结果严格按原归档顺序接纳。并发读提前量受 worker 数限制，取消会关闭读取队列。进度分别显示归档 worker、已读完的包和各活动包的当前成员。途中损坏的归档不能贡献不完整候选。

新增验证覆盖：真实 gzip tar/ZIP 串并行结果一致；真实线程重叠但较晚归档不能抢先覆盖；路径/文件名歧义保持拒绝；半途损坏的候选不接纳；仅在输入身份一致时复用旧运行已接纳的解压文件，复用不扩大选择池，且新运行仍进行全解码与 SHA 核验。未从旧运行复用训练结果或特征。

相关测试 50 passed；最终整套回归 **270 passed、1 skipped**，44.18 秒，旧 v3 warning 一条。Ruff、Shell 语法及 diff 检查通过。尚未测量 A100/NAS 的归档并发提速；8 路是可配置的初始并发值，不承诺 8 倍加速。
