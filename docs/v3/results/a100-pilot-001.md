# M2 diagnostic: paired 4×A100 pilot, 100 updates per arm

Recorded 2026-11-07. Tracking: [issue #4](https://github.com/YanYaoyuan/TRACE-VL/issues/4), implementation: [PR #3](https://github.com/YanYaoyuan/TRACE-VL/pull/3).

**Outcome:** the compressed path reduces reported visual tokens and full-attention KV, with an accuracy cost relative to the native model. This run does **not** establish a transition-representation advantage over budget-matched pooling. M2 remains open.

## Provenance and version boundary

- Model/trainer implementation: `f37d2d306800089f714af33b7053e75652b6950c`, before the emission-learning change in `a7447dd`.
- Installation/evaluation tooling: PR #5 (`dbd0d55`, `3681e1b`). The owner ran a pasted standalone shell equivalent of the evaluation workflow on the cloud host.
- Training helper: `tools/stage1` from the handoff commit `a96583054415720c1e000191594ad101ab321191`; paired module/LoRA snapshots and per-rank resource records were used.
- Source of A100 evidence: owner-supplied terminal output, including rank resource JSON, FP32 equality results and the complete final `summary.json`. The numerical summary is preserved in [a100-pilot-001-summary.json](a100-pilot-001-summary.json), with formatting only changed.
- The reviewer ran local 5090 code checks and functional smokes, but did not access the A100 server. Raw cloud checkpoints, predictions, resolved YAMLs and the validation-manifest hash are not included in this report. Confidence intervals are reported from the supplied summary, not independently recomputed from raw predictions.
- These results do not validate `a7447dd` or any subsequent training run. Reproducing the historical evaluation requires the old implementation and original manifests/configs; applying the current checkout to the old output directory should fail its identity checks.

## Procedure performed

1. Download/extract the YouTube 0–30 s media shards and prepare audited `train.jsonl` / `val.jsonl`. Keep media under the same root used by the annotation-relative paths. Do not regenerate the split when comparing arms.
2. Install the pinned training environment through Aliyun using `bash scripts/setup_aliyun.sh`. This remaps artifact URLs in an isolated lock copy, preserving versions and hashes, including cu128 wheels.
3. Run the FP32 fidelity gate on GPU 0:

   ```bash
   CUDA_VISIBLE_DEVICES=0 uv run --locked --no-sync python -m trace_vl v3 check \
     --config configs/v3/a100-pilot-transition.yaml \
     --steps 4 --dtype float32 --device cuda:0
   ```

   Result: identical 865-token sequences; maximum native/reference difference `2.6702880859375e-05`; zero-gated v3/native difference `0.0`; gate passed. This was the CLI's synthetic four-step fidelity check (`video: null`), not a held-out accuracy evaluation.
4. Train transition and B4 sequentially with `torchrun --nproc_per_node=4`, via the handoff's `cloud_train.sh` / `train_with_checkpoints.py`. Set `TRACE_STEPS=100`, `TRACE_GPUS=4`, `TRACE_CLIP_SECONDS=30`, and use separate `pilot-transition` / `pilot-b4` output folders. All ranks completed. The evaluated paired snapshots are `checkpoints/step-00100/{modules.pt,lora,checkpoint.json}`.
5. Run the single evaluation shell. It verifies manifests, video separation, completed ranks, paired weights and run identities; summarizes rank-0 gate logs; audits the first eight sorted training videos for up to 30 seconds each; evaluates native, transition and B4; and rejects incomplete, duplicate, mixed-run or errored predictions before scoring.

   Equivalent repository entry point (use the checkout/configs matching the intended run):

   ```bash
   export TRACE_RUNS=/path/to/tracevl-runs/a100-pair-001
   export TRACE_DATA_DIR=/path/to/tracevl-data/stage1-30s-001
   export TRACE_VIDEO_ROOT=/path/to/extracted-videos
   bash scripts/evaluate_a100_pilot.sh --check-only
   bash scripts/evaluate_a100_pilot.sh
   ```

6. Read `pilot-eval/summary.json`. Individual accuracy intervals use the core scorer's whole-video bootstrap. Paired differences use 4,000 whole-video bootstrap replicates, seed 7. The independent resampling units are the 29 videos, not 488 independent questions.

## Results

| Metric | Native | Transition | B4 pooled |
|---|---:|---:|---:|
| Correct / questions | 431 / 488 | 416 / 488 | 418 / 488 |
| Accuracy | 88.32% | 85.25% | 85.66% |
| Accuracy 95% CI | [85.51, 90.95]% | [81.69, 88.52]% | [82.14, 88.96]% |
| Mean visual tokens / step | 196.3012 | 36.7462 | 36.7462 |
| Mean full-attention KV (MiB) | 41.2190 | 9.0718 | 9.0718 |
| Maximum observed KV (MiB) | 71.4609 | 14.9297 | 14.9297 |
| Mean answer-phase time | 95.69 ms | 120.29 ms | 119.13 ms |

The fixed training-video budget audit passed with `budget_gap=0.0`. Aggregate validation token/KV metrics also agree between transition and B4. The calibration result alone is not a claim of per-example budget equality over every possible input.

| Paired comparison | Accuracy difference | 95% video-bootstrap CI |
|---|---:|---:|
| Transition − B4 | −0.4098 pp | [−1.8480, +1.0438] pp |
| Transition − native | −3.0738 pp | [−5.7260, −0.4090] pp |

Relative to native, the reported mean visual-token count falls by **81.28% (5.34× fewer)** and mean KV by **77.99% (4.54× smaller)**. The transition arm retains **96.52% of native accuracy by point estimate**, but is significantly below native on this pilot's paired interval. The interval against B4 crosses zero: it supports neither superiority nor equivalence. The M2 requirement of +2 pp over B4 is not met.

`lm_tokens_per_step` averages visual-step counts over question records. `kv_mb` is calculated using `bytes / 2**20` and covers full-attention KV, not total GPU memory or GDN state. `answer_seconds` covers answering and immediate statistics collection; it excludes video ingestion and is not an end-to-end throughput measurement. Recorded answer time is about 25.7% higher for transition; no speedup claim follows from token reduction alone.

## Developer follow-up before a larger run

- Keep this old-objective pilot frozen as a control. Re-run both arms from matched initializations under the new gate objective; do not mix these scores with `a7447dd` results or reuse its evaluation output directory.
- **Check the budget target:** `a7447dd` applies the two-sided target to expected **P-step** tokens. With `gist=8`, `slots=8`, `max_active=8`, the attainable range is 8–32; the inherited `target_tokens_per_step=40` is impossible. Add a configuration guard and choose a feasible, predeclared target (20 is a proposed pilot setting, not a measured optimum). No objective/config change is silently applied by this integration.
- Check train-time and deterministic eval-time `active_slots_mean`, active-P-step fraction, expected/actual P tokens, and CST memory depth. Sampling during training alone is insufficient evidence that the eval gate recovers.
- Re-audit actual budgets for independently trained checkpoints. `pooled_match` inside each run is not proof that two separately trained gate trajectories have matching budgets.
- Run a paired 100-update mechanism pilot first; expand to longer training and multiple seeds after gate activity and budget checks pass. Treat this split as development validation after inspecting it; reserve a separate test set for final claims.
- Add monitoring-specific labels and long-gap tasks separately. This short-video multiple-choice pilot does not validate surveillance alerts, cross-camera behavior or long-term evidence retention.
