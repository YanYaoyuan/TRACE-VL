# Endpoint reader training flow

`core_vlm.endpoint_reader.EndpointReaderEpisode` adds an answer-only LM LoRA update on disposable forks of the existing native hybrid stream. The live stream is question-blind and retains bounded KV plus the model's recurrent/conv state. This primitive supports the existing window/reservoir/full policies; it is not a full training launcher or a learned writer.

One source episode uses one set of parameter values. Build its complete visual prefix under `torch.no_grad`, not `inference_mode`. Seal the actual endpoint before presenting questions. Teacher forcing appends the question tail and preceding gold-answer tokens only on a disposable cache fork; prompt/visual tokens have no loss. Include the tokenizer's intended answer-termination token in the supplied answer IDs. Over-budget answers raise instead of being truncated silently.

The prefix state/KV is detached. Answer CE retains gradients to LM LoRA only; this is truncated reader adaptation, not full-prefix BPTT or training of the visual encoder/history writes. Existing `functional_linear_cache` updates prevent overwriting Gated DeltaNet states needed by backward. Snapshots check that question forwards do not mutate live KV/state/positions/owners or retention RNG.

`train_step` averages each question's mean-token CE within a source, accumulates its question gradients, clips them and performs exactly one optimizer update. The optimizer must own exactly the LoRA parameters; the model stays in eval mode with trainable LoRA for deterministic, dropout-free execution. The episode closes after an attempted update. Standard PyTorch parameter-version changes outside this API also invalidate cached prefixes. Rebuild the source prefix under the updated weights before another source episode; mixing stale keys/values with new LoRA is forbidden. Version checks do not claim detection of arbitrary unsafe external `.data` mutations.

The native endpoint pilot has 64 metadata-selected training source groups and 317 QA records; 16 other groups are isolated for inspection. Its videos span approximately6–11min. That preparation is an engineering cohort with weak native QA, not verified delayed-memory supervision. No dev/reserved QA belongs in this flow. Native source records must be adapted to question tail tokens and full answer IDs without inventing earlier cutoffs, evidence times or answer-dependent writes. Core data validation/actual PTS and native prompt packing remain caller responsibilities.

Matched training arms must share source/question order, initialization, trainable layers, update count, optimizer and declared retention/compute constraints. Equal retained visual steps do not establish equal total KV bytes. A later writer can use separately defined offline utility labels, but is not implemented here. Current-perception preservation and official benchmark evaluation remain necessary beyond this primitive.

Validation starts on hosted CI, with a real tiny Qwen3.5 hybrid LM and PEFT LoRA: cached-versus-uncached answer CE, actual LoRA gradients/updates, frozen base/detached prefix, live-cache isolation, source averaging, stale-cache rejection and failure semantics. ## Matched endpoint training pilot

`python -m trace_vl.core_vlm.train_endpoint_reader` consumes the pinned private64-source/317-QA manifest. It accepts only the declared `candidate_train_pilot` records, null evidence and unchanged full-container-end query times. Source/group identity and actual local bytes are checked before constructing the model. Actual frame PTS must be finite, strictly increasing and zero-origin; sampling floors2fps slots to available frames, removes duplicates and keeps complete pairs. A query slightly after the final available frame remains unchanged. Timestamps inside native prompts retain the existing explicitly audited native-index/FPS approximation.

Reservoir8+32 and window40 start from the same validated Plain adapter, seed17, source/question order, LM LoRA rank8/alpha16/dropout0, AdamW learning rate1e-5/zero weight decay, clip1, one mean-question update per full source. Both carry recurrent state and retain40 visual steps; report real KV token/byte counts separately. Windows retain the latest40steps of the continuously carried stream, not a fresh replay. No learned writer or perception-preservation loss is introduced. Initial adapter digests must match across arms.

The fixed64-update schedule starts with shortest and longest sources (duration, then ID), then a stable question-blind hash order; QA order is by saved ID. `--stop-after 2` is the cost/recovery stage and does not change run identity or the final64-update schedule. No checkpoint or training-loss result determines source selection. First-source native packing/short cached-versus-uncached parity is checked on each invocation. These checks do not bound long-stream numerical drift. Source completion uses existing atomic adapter/Adam/CPU+CUDA RNG checkpoints; resuming verifies all committed checkpoint hashes and restores parameters/optimizer/RNG before rebuilding a fresh source prefix. An exclusive run lock prevents duplicate writers. Incomplete temporary checkpoints are ignored; corrupt committed ones stop recovery.

Predeclared execution gates: first two sources in each arm under1,200s, positive finite gradients, at most18GiB peak owned allocated memory and a complete two-source checkpoint. Their measured maximum source time projects the remaining schedule; continue only if the projection is below the10,800s full-stage ceiling. Full-stage supervisor touches only its own worker process groups. Require24GiB free per selected device,90GiB free disk and cap pilot outputs at64GiB; do not stop unrelated tasks or alter installed kernels/packages. Training loss, source counts and throughput are engineering observations; no held-out quality or memory gain is inferred. Independent development/perception/history controls are required before scaling beyond this pilot.
